1. INTRODUCTION                                     *ansible-vault-intro*

ansible-vault.nvim is a Neovim plugin for working with Ansible Vault files
and inline `!vault` YAML values, built so that decrypted content never
reaches the disk. See |ansible-vault-security|.

- Encrypt, decrypt, view and edit whole files
- Create a new encrypted file with |:VaultCreate|
- Encrypt, view and decrypt inline `!vault` values, by selection or under
  the cursor
- Rekey encrypted files
- Reads `ansible.cfg` and `ANSIBLE_*` variables the way Ansible does
- Preserves the vault ID label carried by a format 1.2 header
- Interactive password input, never cached to disk or memory
- Command-line credential overrides with completion

==============================================================================
2. REQUIREMENTS                               *ansible-vault-requirements*

- Neovim >= 0.12
- `ansible-vault` command available in PATH, or its path given to `setup()`

                                            *ansible-vault-version-policy*
This plugin tracks the CURRENT Neovim release only. Older versions are not
worked around and are not tested; they may happen to work, but that is not a
promise. Keeping a single target is what keeps the plugin maintainable with
the effort available. |:checkhealth| reports whether your version is
supported.

3. COMMANDS                                       *ansible-vault-commands*

All commands accept optional vault credential overrides as arguments.

                                                 *:VaultEncrypt*
:VaultEncrypt [args]
    Encrypt the current buffer with ansible-vault. The buffer content
    is replaced with ciphertext. Use `:write` to persist.

                                                 *:VaultDecrypt*
:VaultDecrypt [args]
    Decrypt the current encrypted buffer in place and enter plaintext
    editing mode. The buffer shows the decrypted content, but `:write`
    re-encrypts before touching the file, and Neovim's swap file, undo
    file and backup file are all disabled for it. The buffer stays
    decrypted after a write so editing can continue; run |:VaultEncrypt|
    to return it to ciphertext, or `:edit!` to reload the file.
    See |ansible-vault-security|.

                                                 *:VaultCreate*
:VaultCreate[!] {file}
    Create a new Ansible Vault file. Opens an empty, hardened buffer;
    the file is not created until `:write`, and is only ever written
    encrypted. Fails if {file} already exists unless `!` is given.

                                                 *:VaultView*
:VaultView [args]
    View the decrypted content of an encrypted buffer in a read-only
    floating window. Press `q` or `<Esc>` to close.

                                                 *:VaultEdit*
:VaultEdit [args]
    Edit an encrypted file in a secure scratch buffer. The scratch
    buffer has `swapfile` and `undofile` disabled. On `:write`, the
    content is encrypted and atomically written back to the original
    file.

                                                 *:VaultRekey*
:VaultRekey [args]
    Rekey the current file-backed encrypted buffer. Requires
    `new_vault_id`, `new_password_file`, or a `--new-vault-*` argument.

                                                 *:VaultEncryptString*
:[range]VaultEncryptString [args]
    Encrypt the selected text as an inline YAML vault string. When
    a full YAML key/value line is selected, the key is preserved.

                                                 *:VaultDecryptString*
:[range]VaultDecryptString [args]
    Decrypt a selected inline YAML vault string in place.

                                                 *:VaultViewString*
:[range]VaultViewString [args]
    View a selected inline YAML vault string in a floating window.

                                             *:VaultEncryptStringUnderCursor*
:VaultEncryptStringUnderCursor [args]
    Encrypt the YAML value under the cursor without making a visual
    selection.

                                             *:VaultViewStringUnderCursor*
:VaultViewStringUnderCursor [args]
    View the inline vault block under the cursor.

                                           *:VaultDecryptStringUnderCursor*
:VaultDecryptStringUnderCursor [args]
    Decrypt the inline vault block under the cursor in place.

> Note: For visual mode keymaps mapping to the range-accepting commands,
  use `:` (colon) form, e.g. `:VaultEncryptString<cr>`, not `<cmd>`
  form. This ensures the correct visual range is passed. See
  |ansible-vault-keymaps|.

                                                *ansible-vault-command-args*
Supported command-line arguments (can be passed to any vault command):

    `--vault-password-file <path>`      can be repeated
        Override `password_files` for this operation.

    `--vault-id <id>`                   can be repeated
        Override `vault_ids` for this operation.

    `--ask-vault-password`
        Prompt for this operation, ignoring every other credential.
        Handled by the plugin: ansible-vault puts this flag and
        `--vault-password-file` in one mutually exclusive group, and the
        child process has no tty to prompt on.

    `--encrypt-vault-id <label>`
        Override `encrypt_vault_id` for this operation.

    `--new-vault-password-file <path>`  (VaultRekey only)
    `--new-vault-id <id>`               (VaultRekey only)
        Mutually exclusive, as in ansible-vault itself.

    A credential flag replaces the configured credentials rather than
    adding to them. An unrecognised flag or a stray argument is an error:
    a typo used to be ignored and fall through to a password prompt,
    which reads as "the credential was not found".

    Quoted arguments are supported for paths with spaces, e.g.
    `:VaultView --vault-password-file '/path with spaces/pass'`

                                                *ansible-vault-keymaps*
Suggested keymaps (not set by the plugin): >

    vim.keymap.set("n", "<leader>ve", "<cmd>VaultEncrypt<cr>")
    vim.keymap.set("n", "<leader>vd", "<cmd>VaultDecrypt<cr>")
    vim.keymap.set("n", "<leader>vv", "<cmd>VaultView<cr>")
    vim.keymap.set("n", "<leader>vE", "<cmd>VaultEdit<cr>")
    vim.keymap.set("n", "<leader>vr", "<cmd>VaultRekey<cr>")
    vim.keymap.set("v", "<leader>vs", ":VaultEncryptString<cr>", {silent=true})
    vim.keymap.set("v", "<leader>vS", ":VaultDecryptString<cr>", {silent=true})
    vim.keymap.set("v", "<leader>vv", ":VaultViewString<cr>", {silent=true})
    vim.keymap.set("n", "<leader>vs", "<cmd>VaultEncryptStringUnderCursor<cr>")
    vim.keymap.set("n", "<leader>vS", "<cmd>VaultDecryptStringUnderCursor<cr>")
<
Note: Visual mode mappings use `:` form (not `<cmd>`) so that the
current visual range is correctly passed to the command.

4. CONFIGURATION                                 *ansible-vault-config*

Call |ansible-vault.setup()| with your settings: >

    require("ansible-vault").setup({
      vault_ids = nil,
      password_files = nil,
      ask_password = false,
      encrypt_vault_id = nil,
      new_vault_id = nil,
      new_password_file = nil,
      ansible_vault_path = nil,
    })
<
There is one key per `ansible-vault` flag, named after it, so whatever the
Ansible documentation tells you to pass is spelled the same way here. An
unknown key is an error rather than being ignored, so a typo or a key left
over from an older version cannot look like it took effect.

                                                 *ansible-vault-config-vault_ids*
`vault_ids` ~
    `--vault-id`, e.g. `"prod@~/.vault_pass"`. A single string or a
    list, because the flag is repeatable. Source paths are expanded
    with |expand()|.

                                                 *ansible-vault-config-password_files*
`password_files` ~
    `--vault-password-file`. A single string or a list. Takes
    precedence over `vault_ids`.

                                                 *ansible-vault-config-ask_password*
`ask_password` ~
    (boolean, default `false`)
    Always prompt, ignoring credentials from `setup()`, `ANSIBLE_*`
    and `ansible.cfg`. Cannot be combined with `vault_ids` or
    `password_files`.

                                                 *ansible-vault-config-encrypt_vault_id*
`encrypt_vault_id` ~
    Vault ID label to use when encrypting. Passed as
    `--encrypt-vault-id`. If `nil`, let ansible-vault choose.

                                                 *ansible-vault-config-new_vault_id*
`new_vault_id` ~
    `--new-vault-id` target for |:VaultRekey|.

                                                 *ansible-vault-config-new_password_file*
`new_password_file` ~
    `--new-vault-password-file` target for |:VaultRekey|. Mutually
    exclusive with `new_vault_id`.

                                                 *ansible-vault-config-ansible_vault_path*
`ansible_vault_path` ~
    Custom path to the `ansible-vault` executable. This is also how
    to use a conda environment: point it at
    `<env>/bin/ansible-vault`.

5. PASSWORD SOURCES                             *ansible-vault-passwords*

The plugin resolves credentials in this order:

1. Per-command overrides                   |ansible-vault-command-args|
2. `ask_password`                          |ansible-vault-config-ask_password|
   then `password_files`                 |ansible-vault-config-password_files|
   then `vault_ids`                           |ansible-vault-config-vault_ids|
3. `ANSIBLE_*` environment variables
4. `ansible.cfg`
5. Interactive password prompt

Layers 3 and 4 are Ansible's own. When credentials come from there the
plugin passes no credential flags at all and simply runs `ansible-vault`
in the right directory, letting it resolve them. Passing
`--vault-password-file` on top of an `ansible.cfg` that already sets one
makes `ansible-vault encrypt` fail with:

    The vault-ids default,default are available to encrypt

                                            *ansible-vault-ansible-cfg*
ANSIBLE.CFG DISCOVERY

Ansible only looks for `ansible.cfg` in the process working directory and
does not search upward. In an editor the working directory is rarely the
playbook directory, so this plugin walks up from the current file:

1. `$ANSIBLE_CONFIG` (a file, or a directory containing `ansible.cfg`)
2. `ansible.cfg` or `.ansible.cfg`, searching upward from the current file
3. `~/.ansible.cfg`
4. `/etc/ansible/ansible.cfg`

`ansible-vault` is then run with its working directory set to wherever the
config was found, so relative paths inside it resolve exactly as Ansible
resolves them, which is relative to the config file itself.

These keys are read from `[defaults]`, and the matching environment
variables override them: `vault_password_file`, `vault_identity_list`,
`vault_identity`, `vault_encrypt_identity` and `ask_vault_pass`.

Run |:checkhealth| to see which config was found and which credential
source is actually in effect.

                                            *ansible-vault-vault-id-label*
VAULT ID LABELS

A file encrypted with a vault ID carries the label in its header:

    $ANSIBLE_VAULT;1.2;AES256;prod

Re-encrypting such a file with a plain `--vault-password-file` would
rewrite it as `$ANSIBLE_VAULT;1.1;AES256` and drop the label. The plugin
reads the label before decrypting and names it again on the way back, so
|:VaultEdit|, |:VaultDecrypt| plus `:write`, and |:VaultRekey| all leave
the header intact.

Most commands also accept temporary credential overrides via
command-line arguments. See |ansible-vault-command-args|.

If the password is wrong on a decrypt operation, the cached
password is automatically invalidated, prompting for a new one
on the next attempt.

6. API                                               *ansible-vault-api*

                                     *ansible-vault.setup()*
`setup(opts)` ~
    Configure the plugin. See |ansible-vault-config|.

                                     *ansible-vault.is_encrypted()*
`is_encrypted(content)` ~
    Check if content (string or list of lines) is vault
    encrypted. Returns `boolean`.

                                     *ansible-vault.is_buffer_encrypted()*
`is_buffer_encrypted(buf?)` ~
    Check if a buffer is vault encrypted.

                                     *ansible-vault.parse_header()*
`parse_header(content)` ~
    Parse a `$ANSIBLE_VAULT` header. Returns
    `{ version, cipher, label }` or `nil`. See
    |ansible-vault-vault-id-label|.

                                     *ansible-vault.create()*
`create(opts?)` ~
    Create a new Ansible Vault file. The path is taken from
    `opts.positionals[1]`; set `opts.bang` to overwrite. See
    |:VaultCreate|.

                                     *ansible-vault.encrypt()*
`encrypt(buf?, opts?)` ~
    Encrypt the current or specified buffer.

                                     *ansible-vault.decrypt()*
`decrypt(buf?, opts?)` ~
    Decrypt the current or specified buffer.

                                     *ansible-vault.view()*
`view(buf?, opts?)` ~
    View decrypted buffer content in a floating window.

                                     *ansible-vault.edit()*

    Edit an encrypted buffer in a secure scratch buffer

                                     *ansible-vault.rekey()*

    Rekey the current file-backed encrypted buffer.

                                     *ansible-vault.cleanup()*

                                     *ansible-vault.encrypt_string()*

    Encrypt visually selected text as an inline YAML vault

                                     *ansible-vault.decrypt_string()*

    Decrypt a selected inline YAML vault string in place.

                                     *ansible-vault.view_string()*

    View a selected inline YAML vault string.

                                     *ansible-vault.encrypt_string_under_cursor()*
`encrypt_string_under_cursor(opts?)` ~
    Encrypt the YAML value under the cursor.

                                     *ansible-vault.decrypt_string_under_cursor()*

    Decrypt the inline vault block under the cursor.

                                     *ansible-vault.view_string_under_cursor()*

7. USER EVENTS                                   *ansible-vault-events*

The plugin emits |User| autocommands after successful operations:

The plugin emits exactly one pattern, `AnsibleVaultOperation`, so a
single autocommand can react to everything and filter on the payload.

The event `data` contains:

    `op`     one of `"encrypt"`, `"decrypt"`, `"view"`, `"edit"`,
           `"save"`, `"rekey"`, `"create"`
    `scope`  `"file"` or `"inline"`
    `buf`    the buffer the operation applied to
    `file`   the file path, when the operation touched one

Example: >

    vim.api.nvim_create_autocmd("User", {
      pattern = "AnsibleVaultOperation",
      callback = function(event)
        vim.print(event.data.operation)
      end,
    })
<

8. SECURITY                                     *ansible-vault-security*

The goal is that decrypted content never reaches the disk, including
after `kill -9` or a power loss.

WHAT THE PLUGIN GUARANTEES

- No swap file. 'swapfile' is reset before plaintext enters a buffer,
  which also deletes any swap file that already existed for it.
- No undo file. 'undofile' is off for decrypted buffers, and the undo
  history is cleared across every encrypt/decrypt transition.
- No backup file. Decrypted buffers use 'buftype' `acwrite`, so Neovim
  skips its own write path entirely and 'backup' and 'writebackup'
  never apply.
- No accidental plaintext write. Every form of `:write`, including
  `:write {other-file}`, goes through the plugin and encrypts first.
- No password on disk. Interactive passwords are collected with
  |inputsecret()| and passed to `ansible-vault` through the child
  process environment, read back by a static helper script in
  `stdpath("run")` that contains no secret. Where that is not possible
  the plugin falls back to a `0600` temporary file, removes it on exit,
  and |:checkhealth| reports which mode is in use.
- Nothing secret in messages. Process stdout is never echoed into an
  error, because `ansible-vault decrypt` can write plaintext to stdout
  and still exit non-zero. Any argv the plugin does surface has its
  credential values redacted.
- No plaintext argv. Content goes over stdin and passwords are passed
  by reference, so neither appears in `ps`.
- Atomic writes. Encrypted output is written to a sibling temporary
  file, `fsync`ed, then renamed into place, inheriting the original
  file's mode.
- |:VaultEdit| additionally refuses to overwrite the original file if
  it changed on disk while the scratch buffer was open.
- Interactive passwords are never cached. Each operation prompts for
  its own, so no secret sits in Neovim's heap between operations.

WHAT IS STILL UP TO YOU

These are global Neovim settings the plugin deliberately does not
change. |:checkhealth| warns when they are enabled.

- 'shada' persists registers, so text you *yank* out of a decrypted
  buffer or the |:VaultView| window is written to the shada file on
  exit. Consider `:set shada=` while working with secrets.
- 'backup' applies to files written outside this plugin.
- Decrypted content is in Neovim's memory while you view or edit it, so
  it can reach the OS swap partition or a core dump. Review your other
  plugins, clipboard settings and terminal or session recording.

9. HEALTH CHECK                                 *ansible-vault-health*

Run |:checkhealth| to verify your setup: >
    :checkhealth ansible-vault
<
The health check reports:
- `ansible-vault` executable availability
- Which credential source is actually in effect, resolved through the
  same code the real operations use
- The `ansible.cfg` that was found, how it was found, and the directory
  `ansible-vault` will run in
- Password file readability and 0600 permissions, recognising executable
  password scripts as the supported configuration they are
- Vault ID label sources and `encrypt_vault_id` consistency
- |:VaultRekey| target configuration
- Whether interactive passwords can be kept off disk entirely
- Global options that could still persist decrypted content

10. STATUSLINE INTEGRATION                  *ansible-vault-statusline*

Use |ansible-vault.is_buffer_encrypted()|. It inspects the buffer on
every call rather than relying on state an earlier operation left
behind: >

    -- Manual integration
    if require("ansible-vault").is_buffer_encrypted() then
      -- buffer is encrypted
    end

    -- lualine integration
    require("lualine").setup({
      sections = {
        lualine_x = {
          {
            function()
              return require("ansible-vault").is_buffer_encrypted() and "[VAULT]" or ""
            end,
          },
        },
      },
    })
<
