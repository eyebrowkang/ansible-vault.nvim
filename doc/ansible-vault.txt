1. INTRODUCTION                                     *ansible-vault-intro*

Encrypt, decrypt, view, edit and rekey whole Ansible Vault files or individual
inline YAML `!vault` values. |:VaultCreate| creates encrypted files only.
Range encryption provides Ansible's `encrypt_string` capability.

Choose the command by what you want to save:

    Decrypt       :write saves PLAINTEXT from the current buffer.
    Create/Edit   :write encrypts to the fixed file target.
    Inline Edit   :write encrypts into the source BUFFER, not its file.
    View          Read-only; all writes are refused.

Quick start: open a vault file and run |:VaultEdit|. Enter the password if
prompted, make changes in the separate buffer, then use `:write` to encrypt
and save. Passwords are not cached, so saving may prompt again. Use `:wq` to
save and close. No password file or `setup()` call is required.

For an intentional plaintext file, use |:VaultDecrypt| followed by `:write`.
For protection boundaries, see |ansible-vault-security|.

2. REQUIREMENTS AND INSTALLATION              *ansible-vault-requirements*

                                            *ansible-vault-version-policy*
- Neovim 0.12. Other versions are not guaranteed to work.
- Ansible, with `ansible-vault` in PATH, or its executable path supplied via
  |ansible-vault-config-ansible_vault_path|.

Ansible installation:
https://docs.ansible.com/ansible/latest/installation_guide/intro_installation.html

With lazy.nvim, add this plugin spec: >lua
    { "eyebrowkang/ansible-vault.nvim" }
<
With packer.nvim: >lua
    use { "eyebrowkang/ansible-vault.nvim" }
<
The six commands are available as soon as the plugin is loaded. Calling
|ansible-vault.setup()| is optional. Check installation with: >vim
    :checkhealth ansible-vault
<

3. COMMANDS                                       *ansible-vault-commands*

All six commands accept the credential arguments documented at
|ansible-vault-command-args|. Only Create accepts a command bang (`!`).

                                                  *ansible-vault-scope*
TARGETS AND RANGES

- |:VaultCreate| takes one filename, does not accept a range, and creates
  whole-file vaults only.
- |:VaultEncrypt| without a range ALWAYS encrypts the entire buffer, even
  after an inline decryption. Use `:.VaultEncrypt` for the current line.
- Decrypt, View, Edit and Rekey choose their target in this order:
    1. Explicit range: one complete inline `!vault` block.
    2. Vault header on line 1: the whole buffer.
    3. Otherwise: the inline `!vault` block under the cursor.

Pass a visual selection explicitly, for example `:'<,'>VaultEncrypt`.
A later normal-mode command does not reuse an earlier visual selection.
See |ansible-vault-keymaps| for visual mappings.

An inline range must contain exactly one complete scalar or vault block.
Truncated blocks, multiple values and neighbouring YAML entries are rejected
without changing the buffer. For a multiline scalar, select its key and all
content lines, not its parent: >yaml
    service:
      "private key": |-
        first line
        second line
<
Here, select `"private key"` and its two content lines. Encryption keeps the
key and replaces only the value. Quoted keys, indentation, list prefixes and
value content are preserved, including meaningful whitespace and newlines.
Scalar presentation may change; decryption can use a literal block scalar
for a multiline value. Select the complete result to encrypt it again.

Keyless `!vault` blocks, including list items, support Decrypt, View, Edit
and Rekey. Other YAML entries are left unchanged.

                                                 *:VaultEncrypt*
:[range]VaultEncrypt [args]
    Without a range, replace the whole buffer with ciphertext. This does
    not save the file; use `:write` afterwards.

    With a range, replace one scalar with an inline `!vault` value. For
    example, `password: secret` becomes: >yaml
        password: !vault |
          $ANSIBLE_VAULT;1.1;AES256
          3132333435...
<
    Save the source YAML yourself. Range encryption does not imply that the
    rest of the buffer contains no secrets. See |ansible-vault-security|
    for the effect of encryption on persistent undo.

                                                 *:VaultDecrypt*
:[range]VaultDecrypt [args]
    Replace whole-file ciphertext or one inline `!vault` block with
    plaintext in the current buffer. `:write` SAVES PLAINTEXT: no
    re-encryption, second password prompt or extra confirmation.

    For inline decryption, other vault values remain encrypted. `:write`
    saves the YAML as shown, including any decrypted values. To encrypt
    only one value again, select its complete scalar and use
    `[range]VaultEncrypt`. Without a range, Encrypt encrypts the whole YAML.

    A file changed on disk since decryption requires `:write!` to overwrite
    it. Review the changes before forcing a save.

    A whole-buffer `:write {other-file}` from a named buffer writes a
    plaintext copy without marking the original buffer saved. From an
    unnamed buffer, `:write {file}` adopts the filename and marks it saved.
    `:saveas {file}` is also an intentional plaintext save. Partial writes
    and append writes are refused; see |ansible-vault-security|.

    The current buffer stays protected after a plaintext save. The saved
    plaintext file, opened fresh later, is an ordinary file. To put
    ciphertext back on disk, use |:VaultEncrypt| then `:write`. To edit
    without saving plaintext at all, use |:VaultEdit| instead.

    `:edit!` discards unsaved changes and reloads what is on disk. After a
    plaintext save, that is plaintext, not the original encrypted file.

                                                 *:VaultCreate*
:VaultCreate[!] {file} [args]
    Open an empty protected buffer for a new encrypted file. This command
    is file-only; it does not create inline values. The file is not created
    until the first successful `:write`. Every save writes ciphertext to
    the same fixed target.

    An existing file requires `:VaultCreate!`; it is not overwritten before
    saving. A path already open in another buffer is refused even with `!`.
    The target directory must already exist.

    `:write {other-file}` and `:saveas` cannot redirect this buffer's output.
    `:wq` and `:x` wait for encryption and saving; failure leaves the buffer
    open with your changes. Credentials are obtained for each save.

                                                 *:VaultView*
:[range]VaultView [args]
    Show decrypted whole-file content or one inline value in a protected,
    read-only floating window. The source buffer is unchanged. No plaintext
    editing file is created. Press `q` or `<Esc>` to close the view.

    ALL writes are refused, including `:write`, `:write {path}`, `:saveas`
    and `:%write {path}`. Unlike Edit/Create, View has no encrypted save
    operation either. Use |:VaultDecrypt| if you want plaintext on disk.

                                                 *:VaultEdit*
:[range]VaultEdit [args]
    Open decrypted content in a separate protected editing buffer. Opening
    it and each subsequent save obtain credentials separately; interactive
    passwords are not cached, so both can prompt.

    Whole file:
        Requires an encrypted, file-backed buffer with no unsaved changes.
        `:write` encrypts and saves to the original file. The editing
        buffer remains open for further changes and repeated saves.

    Inline value:
        `:write` encrypts the value back into the source BUFFER only.
        Return to the source buffer and use `:write` to save the YAML file.
        Unsaved source changes already present when Edit opened are kept.
        After a successful write-back, you can edit and save the value
        again. Keyless blocks and list items are supported.

        Any source buffer change after opening blocks write-back, even
        outside the selected block. Renaming or deleting the source also
        blocks it. `:write!` cannot override these conflicts. It can
        override a source FILE change when the source buffer is unchanged;
        this still does not write the source file. Recovery steps are at
        |ansible-vault-troubleshooting|.

    The target is fixed. `:write {other-file}` and `:saveas` cannot redirect
    the output. `:wq` and `:x` wait for saving to finish. Failed saves keep
    the buffer open and retain unsaved edits.

    Decrypting an inline value inside a whole-file Edit buffer does not
    change its save behaviour: `:write` still encrypts the whole file.

                                                 *:VaultRekey*
:[range]VaultRekey [args]
    Rotate the password using exactly one new-credential argument:
    `--new-vault-password-file {path}` or `--new-vault-id {label@source}`.
    Old credentials come from the normal sources or command overrides.

    Whole file:
        Requires an encrypted, file-backed buffer with no unsaved changes.
        Saves new ciphertext directly to the original file and updates
        the buffer. A failure or intervening file change leaves the
        original file untouched.

    Inline value:
        Replaces only that ciphertext block in the source buffer; save
        the source YAML yourself. Intermediate plaintext is not inserted
        into the source buffer. Keyless blocks and list items work too.

    A new password file preserves the existing 1.2 label by default.
    `--new-vault-id` can choose a new label. `--encrypt-vault-id` is NOT
    accepted by Rekey. See |ansible-vault-vault-id-label|.

                                                *ansible-vault-command-args*
COMMAND ARGUMENTS

Six argument types are supported. Use a space between a flag and its value.

    --vault-password-file {path}
        All commands. Password file or executable password script.
        Repeatable; replaces the plugin's configured credential selection.

    --vault-id {label@source}
        All commands. Vault identity; repeatable. Replaces the plugin's
        configured credential selection. Sources use Ansible's vault-ID
        syntax, including password files and executable password scripts.

    --ask-vault-password
        All commands. Request interactive input for this operation instead
        of the selected file/ID credentials. Cannot be combined with
        --vault-password-file or --vault-id. On Rekey this requests the
        OLD password; a new-credential argument is still required.

    --encrypt-vault-id {label}
        Encrypt, Create and Edit only. Select the identity for encryption.
        Not accepted by Decrypt, View or Rekey.

    --new-vault-password-file {path}
        Rekey only. New password file; cannot be combined with
        --new-vault-id.

    --new-vault-id {label@source}
        Rekey only. New identity; cannot be combined with
        --new-vault-password-file.

Repeated file/ID flags build the list for this operation, rather than retaining
unused entries from a setup list. If both --vault-password-file and --vault-id
are supplied, password files take precedence. Command overrides do not change
`setup()`. See |ansible-vault-passwords| for Ansible settings and the prompting
exception.

Prompting and new rekey credentials are command arguments, not `setup()` keys.
Unknown flags, missing values, unsupported flags and stray arguments are
errors. Create takes exactly one filename; the other commands take none.

Quote or backslash-escape paths containing spaces: >vim
    :VaultView --vault-password-file '/path with spaces/pass'
    :VaultEdit --vault-password-file /path\ with\ spaces/pass
    :VaultEncrypt --vault-id dev@~/.dev-pass --encrypt-vault-id dev
    :VaultDecrypt --ask-vault-password
    :VaultCreate 'group_vars/prod/private vault.yml'
    :VaultRekey --new-vault-id prod@~/.ansible/new-pass
<
Completion offers each command's supported flags and filenames for Create.

                                                *ansible-vault-keymaps*
KEYMAPS

The plugin sets no mappings. Examples: >lua
    vim.keymap.set("n", "<leader>vc", ":VaultCreate ")
    vim.keymap.set("n", "<leader>ve", "<cmd>VaultEncrypt<cr>")
    vim.keymap.set("n", "<leader>vd", "<cmd>VaultDecrypt<cr>")
    vim.keymap.set("n", "<leader>vv", "<cmd>VaultView<cr>")
    vim.keymap.set("n", "<leader>vE", "<cmd>VaultEdit<cr>")
    vim.keymap.set("n", "<leader>vr", ":VaultRekey ")

    vim.keymap.set("x", "<leader>ve", ":VaultEncrypt<cr>", {silent=true})
    vim.keymap.set("x", "<leader>vd", ":VaultDecrypt<cr>", {silent=true})
    vim.keymap.set("x", "<leader>vv", ":VaultView<cr>", {silent=true})
    vim.keymap.set("x", "<leader>vE", ":VaultEdit<cr>", {silent=true})
    vim.keymap.set("x", "<leader>vr", ":VaultRekey ")
<
Use `:` rather than `<cmd>` in visual mappings so the range is passed.
Create and Rekey mappings leave the command line open for a filename or new
credential. Normal-mode Encrypt always means the whole buffer; the other
range-capable commands follow |ansible-vault-scope|.

4. CONFIGURATION                                 *ansible-vault-config*

                                     *ansible-vault.setup()*
setup(opts) ~
    Optional. The six commands work without it. Calling `setup()` again
    replaces configuration, without changing already-open vault buffers.
    All four settings default to nil: >lua

    require("ansible-vault").setup({
      ansible_vault_path = nil,
      password_files = nil,
      vault_ids = nil,
      encrypt_vault_id = nil,
    })
<
    Unknown keys and wrong value types are errors and leave the current
    configuration unchanged.

                                    *ansible-vault-config-ansible_vault_path*
ansible_vault_path ~
    String: path to the `ansible-vault` executable. nil uses PATH. For
    Conda or another environment, use `<env>/bin/ansible-vault`.

                                         *ansible-vault-config-password_files*
password_files ~
    String or list of strings: password files or executable password
    scripts. Takes precedence over `vault_ids` when both are configured.
    Paths are expanded with |expand()|. Example: >lua
        require("ansible-vault").setup({
          password_files = "~/.ansible/vault-pass",
        })
<
                                              *ansible-vault-config-vault_ids*
vault_ids ~
    String or list of strings: vault identities such as
    `"prod@~/.ansible/prod-pass"`. Source paths are expanded with |expand()|.
    An identity whose source is `prompt` or `prompt_ask_vault_pass` is asked
    for in Neovim, once per operation and separately per identity; the
    password is never cached. This also applies to such an identity inherited
    from `vault_identity_list` in your Ansible configuration.
    Example with multiple identities: >lua
        require("ansible-vault").setup({
          vault_ids = {
            "dev@~/.ansible/dev-pass",
            "prod@~/.ansible/prod-pass",
          },
          encrypt_vault_id = "prod",
        })
<
                                      *ansible-vault-config-encrypt_vault_id*
encrypt_vault_id ~
    String: identity label to encrypt with. Use it to choose among multiple
    labels. With nil, an applicable existing vault label is reused;
    otherwise Ansible chooses. See |ansible-vault-vault-id-label|.

5. CREDENTIALS                                  *ansible-vault-passwords*

Use interactive input, existing files/IDs in `setup()`, or your existing
Ansible configuration. Passwords are obtained for each operation and are not
cached. Opening Edit and each Edit/Create save can prompt separately.
A write after Decrypt saves plaintext and needs no password.

Normal credential selection, highest priority first:

1. Per-command credential arguments          |ansible-vault-command-args|
2. setup(): password_files           |ansible-vault-config-password_files|
3. setup(): vault_ids                     |ansible-vault-config-vault_ids|
4. Ansible environment/configuration; environment variables override the
   corresponding config settings             |ansible-vault-ansible-cfg|
5. Interactive input when no credential source is available

PROMPTING EXCEPTION

`--ask-vault-password` requests interactive input. An effective
`ask_vault_pass = true` also selects interactive input ahead of password
files and vault IDs, INCLUDING command-line credentials. The environment
variable `ANSIBLE_ASK_VAULT_PASS` overrides that config setting: a true
value requests input; false disables the config's request to prompt.

The requested password takes priority, but this is not a promise that
Ansible's other configured identities are removed. Ansible may still use
configured identities when decrypting. Command credentials replace the
plugin's setup selection, not your Ansible configuration.

                                            *ansible-vault-ansible-cfg*
ANSIBLE.CFG DISCOVERY

The first discovered configuration is used, in this order:

1. $ANSIBLE_CONFIG: an existing file, or a directory containing
   `ansible.cfg` or `.ansible.cfg`.
2. `ansible.cfg` or `.ansible.cfg`, walking upward from the current file.
   If its directory is unavailable, start at Neovim's working directory.
3. `~/.ansible.cfg`.
4. `/etc/ansible/ansible.cfg`.

Ansible runs from the discovered config directory. Relative paths inside
that file resolve relative to the config file, not the edited YAML file.
A missing $ANSIBLE_CONFIG target does not stop the remaining search.

Supported [defaults] settings and corresponding environment variables:

    vault_password_file    ANSIBLE_VAULT_PASSWORD_FILE
    vault_identity_list    ANSIBLE_VAULT_IDENTITY_LIST
    vault_identity         ANSIBLE_VAULT_IDENTITY
    vault_encrypt_identity ANSIBLE_VAULT_ENCRYPT_IDENTITY
    ask_vault_pass         ANSIBLE_ASK_VAULT_PASS

Identity lists are comma-separated. Run `:checkhealth ansible-vault` to see
which config and credential source are selected.

                                            *ansible-vault-vault-id-label*
VAULT ID LABELS

A format 1.2 vault records its identity label in the header:

    $ANSIBLE_VAULT;1.2;AES256;prod

For encryption, a command's `--encrypt-vault-id` overrides the setup value.
Otherwise, the existing header label is reused when the selected credentials
can supply it; absent an applicable label, Ansible chooses. If multiple
labels are available, choose one explicitly rather than relying on a default.
Ansible's `vault_encrypt_identity` / `ANSIBLE_VAULT_ENCRYPT_IDENTITY` can
supply that default when no encryption label is otherwise selected.

Edit preserves the existing label with matching credentials, including a
plain password file. Decrypt saves plaintext and therefore has no output
header. A subsequent Encrypt in the same buffer can reuse the previous
label; this is not historical tracking of files reopened later.

For Rekey, `--new-vault-id` explicitly selects the new identity and label.
A new password file keeps the existing label unless another encryption label
is configured. Rekey does not accept `--encrypt-vault-id`; use the new-ID
argument when changing its label.

6. PROTECTION AND LIMITS                         *ansible-vault-security*

The plugin prevents UNINTENDED plaintext copies. It does not block an
intentional plaintext save: |:VaultDecrypt| followed by `:write` writes
plaintext by design.

PROTECTED BUFFERS

- Managed plaintext buffers have 'swapfile' and 'undofile' disabled before
  decrypted content arrives. Their saves do not create Neovim backup copies.
- View/Edit/Create do not create plaintext editing files. Whole-file
  Edit/Create saves contain ciphertext; inline Edit saves ciphertext into
  the source buffer only. View refuses all writes.
- Interactive passwords are not written to files or cached between
  operations. Error messages do not expose raw command output or passwords.
- Failed encryption and conflicting saves do not overwrite the source or
  discard unsaved edits. Existing file permissions are preserved; new files
  written by the plugin are created with mode 0600.
- A Decrypt save intentionally produces plaintext, including temporary output
  used during that save. The current buffer remains protected afterwards.
  Encrypting only a range does not remove its protection. Successful
  whole-buffer encryption restores ordinary writing, but persistent undo
  may remain disabled as described below.

WRITE RESTRICTIONS

Partial writes, such as `:1write {file}`, and append writes, such as
`:write >> {file}`, are refused in managed buffers and View windows.
A whole-buffer `:write {path}` or `:saveas {path}` from a decrypted buffer is
an intentional plaintext save. Create/Edit cannot redirect their fixed
write target; View cannot save at all.

PERSISTENT UNDO

Persistent undo is disabled in protected plaintext buffers. After range
encryption, ordinary `:undo` can still recover the value in memory, but that
buffer has no cross-session undo. A buffer decrypted and re-encrypted in
place also keeps 'undofile' off for its remaining lifetime; `:edit!` does
not restore it.

Reloading while a buffer is still managed can restore ordinary options but
clears its undo history. These effects are buffer-local: a fresh buffer
opened for the same file later is unaffected. Do not manually re-enable
persistent undo on a buffer that has held secrets.

OUTSIDE THIS PROTECTION

- A deliberately saved plaintext file opened fresh later is an ordinary
  file. It is not automatically recognised or protected as a former vault.
- Registers, ShaDa and the clipboard can retain yanked text. The plugin
  does not change global 'shada'; consider `:set shada=` before working
  with secrets, and review your clipboard settings.
- Global 'backup' and 'writebackup' remain unchanged and still apply outside
  managed writes. The health check reports relevant warnings.
- Other plugins, shell commands (including write-to-shell and filter
  commands), external processes and terminal/session recording are not
  controlled by this plugin.
- Plaintext and passwords exist in process memory while used. Memory
  erasure, OS swap, core dumps and access by other processes are not covered.

7. HEALTH CHECK AND TROUBLESHOOTING               *ansible-vault-health*

Run: >vim
    :checkhealth ansible-vault
<
The report checks Neovim support, executable availability, the discovered
config and credential source, password-file readability and permissions,
encryption-label settings, and relevant global privacy options. It does not
prompt for a password or change your credential setup.

                                            *ansible-vault-troubleshooting*
Command not found ~
    Check that the plugin manager has loaded ansible-vault.nvim. No
    `setup()` call is required. Use Neovim 0.12.

Executable not found ~
    Install Ansible using the link in |ansible-vault-requirements|, or set
    |ansible-vault-config-ansible_vault_path| to its executable. Check the
    executable and selected credential source with the health report.

Wrong password source or unexpected prompt ~
    Check the health report, $ANSIBLE_CONFIG and ANSIBLE_* variables.
    `ask_vault_pass` / `ANSIBLE_ASK_VAULT_PASS` can force a prompt even with
    a command-line password file. Disable the effective ask setting to use
    file/ID credentials. Use `--ask-vault-password` when you want input.

    If secure interactive input is unavailable, check that Neovim's runtime
    directory is writable and owned by you, or use an existing trusted
    password file/script. Do not put a password in a command argument.

Multiple encryption identities ~
    Select the intended label using `encrypt_vault_id` or, for Encrypt,
    Create and Edit, `--encrypt-vault-id`. For Rekey, provide
    `--new-vault-id` instead. Check for unintended Ansible configuration.
    If an error reports a comma in an identity source, use a source path
    without commas.

Invalid inline selection or no block under cursor ~
    Select one complete scalar/block, including its key and content lines,
    or move the cursor into the `!vault` block. Do not include neighbours.
    To encrypt only the current line, use `:.VaultEncrypt`.

Create or whole-file Edit/Rekey refused ~
    Create needs an existing parent directory and a path not open in another
    buffer. Use `:VaultCreate!` only when replacement is intended.
    Whole-file Edit/Rekey need an encrypted file with no unsaved buffer
    changes. Save the intended ciphertext changes before retrying; do not
    save plaintext unless that is what you want on disk.

Write refused ~
    Check which buffer you are in: View never writes, Edit/Create have
    fixed targets, and protected buffers refuse partial/append writes.
    Use a plain `:write` for Edit/Create. Inline Edit requires a second
    `:write` in the source buffer to save the YAML file.

    If the target FILE changed, keep the editing buffer open and inspect
    the new file contents separately, using View/Edit for encrypted content.
    Only use `:write!` when you intentionally want to overwrite those file
    changes. Force does not fix a changed inline source buffer.

Inline Edit source changed, moved or renamed ~
    The old editing buffer retains your changes, but cannot write back to
    the changed source. Undoing the source change does not reset this check.
    To reopen the value without discarding your work:

    1. Keep the old editing buffer open. Give it an unused buffer name,
       for example `:file ansible-vault://recovery`. This does not save or
       export its text; do not try to save from this renamed buffer.
    2. Use `:ls` and `:sbuffer {number}` to open the current source buffer
       in another window. Locate the intended block and run `:VaultEdit`.
    3. Reapply the wanted changes in the new protected editing buffer,
       referring to the old one. Leave the source unchanged while doing so.
    4. Save the new editing buffer, then the source YAML. Only after both
       succeed, close the old recovery buffer with `:bwipeout! {number}`.

    If you do not need the old edits, discard that editing buffer first,
    then reopen Edit on the current source block. Do not export secrets or
    disable protection to work around the conflict.

Reload failed; subsequent write reports E676 ~
    Fix the file path or permissions and reload successfully, or use
    `:bdelete` to close the failed buffer and reopen the file. Do not change
    buffer options to force a write. As with ordinary `:edit!`, a forced
    reload discards unsaved changes.
